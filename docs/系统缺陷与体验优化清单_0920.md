## 一、缺陷清单（按严重度）

### P0 · Redis 密码配置不一致 —— 单次调用 2–25 秒，且会阻塞整个界面 ⚠️ 待修

**实测证据**

| 测量对象 | 结果 |
|---|---|
| `get_redis_client()` 连续调用 | 3.9s / 8.5s / **17–25s** |
| `redis.ping()`（socket_timeout=1.0） | **1835ms** → `AuthenticationError: Client sent AUTH, but no password is set` |
| `redis.ping()`（socket_timeout=0.5） | **9839ms**，同样 AUTH 错误 |
| `GET /api/metrics/prometheus` | **6.6–8.1 秒**（全站中位耗时仅 **7ms**） |

**机制**

1. `.env` / `backend/key.env` 里配置了 `REDIS_PASSWORD`，但**内置 Redis 未启用鉴权**；
2. `core/redis_pool.py::get_redis_client()` 在 `if settings.REDIS_PASSWORD:` 分支里，
   **对每一次调用**都同步 `client.ping()`，失败后再重建一个无密码客户端；
3. 即：**每次拿 Redis 客户端，都要先吃一次注定失败的鉴权往返 + 一次重连**；
4. 内置 Redis 日志（`vendor/redis/runtime/redis-embedded.log`）还显示它
   被反复「启动 → 请求关闭 → 退出」（16:58 / 17:01 / 17:02 / 17:03 多轮），
   连接失败时会吃满 connect timeout。

**放大效应（这是体验上的真正杀手）**

`main.py::db_session_middleware` 用 **全局锁** 包住全部 `/api/` 请求：

```python
if path.startswith('/api/'):
    async with _db_lock:          # ← 所有 API 请求串行
        response = await call_next(request)
```

于是一个 8 秒的 `/api/metrics/prometheus` 会**把界面上所有请求一起堵住 8 秒**。

**修法（三选一或多管齐下）**

1. **最直接**：清掉配置里不一致的 `REDIS_PASSWORD`（`.env` + `key.env` 两处都要改，
   否则会被另一处覆盖）；
2. **治本**：把「密码不匹配」的探测结果 **进程级缓存**（只探一次），
   而不是每次 `get_redis_client()` 都 ping；
3. **隔离**：让 `/api/metrics/prometheus` 不占全局锁，或把 Celery 队列长度
   采集改成后台定时刷新 + 读缓存。

### P1 · 所有 API 请求被全局串行化 ⚠️ 待修

- `db_session_middleware` 的 `_db_lock` 让**并发请求完全排队**。
- 单用户演示无感；但只要有第二个人访问、或某个请求变慢，**全体一起等**（见 P0）。
- 修法：改为**每请求独立 session**（请求结束 `db.session.remove()`），去掉全局锁。
  这是标准做法，但涉及连接池与事务边界，**建议复赛后再动**。

## 二、体验优化方案（按投入产出排序）

### 立刻可做（半天内，风险低）

1. **补 loading 态**：给上述 5 个视图的表格加 `v-loading` + 骨架屏。
   这是**体感提升最明显**的一项——现在点进去是一片空白，用户以为坏了。
2. **消灭剩下 2 处 JSON 弹窗**（研判任务、审批流详情）。
3. **慢请求的可见反馈**：前端 axios 加超时阈值，
   `>1.5s` 显示「正在加载…」提示条，避免用户重复点击。
4. **危险操作二次确认统一化**：现有实现风格不一（有的 `ElMessageBox.confirm`、
   有的直接执行）。统一成一套确认组件，并统一文案格式。

### 值得做（1–2 天）

5. **空态引导**：目前多数空态只有「暂无数据」。改成
   「本案件暂无止付工单 → 【新建工单】」这种**带下一步动作**的空态。
6. **列表可用性**：默认排序（按时间倒序）、关键列固定、分页尺寸可选。
   现在部分表格列多且窄，需要横向滚动。
7. **全局错误提示统一**：401 自动跳登录、403/500 统一文案，
   不再把后端 `error` 原样抛给用户（如 `str(e)` 泄露内部异常）。
8. **演示模式**：一个按钮把演示数据恢复到初始状态
   （复用 `fix_seed_consistency.py` 的幂等修复 + `seed_empty_tables.py`）。
   答辩现场最怕误操作后数据被改乱。

### 加分项（赛前可选）

9. **首屏性能**：`/api/metrics/prometheus` 等非 UI 端点与 UI 请求隔离（见 P0）；
   首屏并发请求合并。
10. **可访问性/键盘**：表单回车提交、Esc 关弹窗、焦点管理。
11. **导出能力**：已有 PDF 报告；可补 Excel/CSV 导出（民警实际工作会用）。

## 三、优先级建议（复赛前）

| 优先级 | 事项 | 理由 |
|---|---|---|
| **1** | 修 Redis 密码不一致（P0） | 一处配置错导致全站百倍延迟，**且拖慢所有演示操作** |
| **2** | 补 5 个视图 loading 态 | 半天工作量，体感提升最大 |
| **3** | 消灭 2 处 JSON 弹窗 | 评委直接可见的"未完成感" |
| 4 | 演示数据一键复位 | 现场容错 |
| 5 | 去掉全局串行锁（P1） | 架构收益大，但风险高 → **赛后** |

> ⚠️ 诚实边界不变：合成数据 ≠ 真实验证；止付冻结为 Mock；
> 「数据不出域」统一口径为**「本地优先 + 出向脱敏」**。
