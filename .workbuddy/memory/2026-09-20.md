## 四、发现并修复：HITL 复核流程的状态机缺陷
- **线索**：库里 `review_tasks` **全部停在 `pending`**（只有 2 条）——
  说明 `assign` / `resolve` 这两步**从来没被走过**。没走过的状态机最容易带病。
- 写了带负向路径的探针，实测出**两类问题**：

### 问题 1（合规）：已完成的复核可被重新分派 / 再次定论
- 对已 `resolved` 的任务再 `assign` → **HTTP 200**，状态被打回 `assigned`，
  而 `review_result` 仍留着 → 出现「**已分派却已有结论**」的自相矛盾状态。
- 对已 `resolved` 再 `resolve` → **HTTP 200**，`review_result` 被**静默覆盖**成新结论。
  → 复核结论是留痕证据，可被覆盖等于闭环失效。
- **修法**（`routes/workflow.py`）：新增 `REVIEW_TERMINAL_STATUS = ('resolved','rejected')`
  与 `_review_status_cn()`；`assign` / `resolve` 入口做**终态门控**，命中返回 400 并提示原结论。
- **顺带修掉一个会吞异常的坑**：`api_assign_review` 只有 `except Exception`，
  没有 `except HTTPException: raise` → 在里面 `raise HTTPException(400)` 会被兜成 **500**。
  （`resolve` 有这一句，所以它的 400 一直正常。）**新增 400 校验前先确认有没有这一句。**

### 问题 2（功能缺口）：`assignReview` 有封装但没有任何 UI 入口
- `api.js:580` 有 `assignReview`，但**全项目无人调用**；复核操作列只有「详情」「处理」。
- 后果：任务永远出不了 `pending` →「**已分派**」这个筛选页签**永远是空的**。

### 5.1 测试侧的大坑：用 `db.session` 读接口写入的结果会读到旧快照
- 现象：`resolve` 接口返回 200、且随后的 R6/R7 能正确看到 `resolved`（返回 400），
  但我自己的断言读出来状态仍是 `assigned`、`review_result` 仍是空 → **3 项假失败**。
- 原因：`db.session` 是 **thread-local** 的，TestClient 在**另一个线程**里跑 ASGI
  应用并提交事务；主线程这条 session 可能仍持有旧快照，`db.session.rollback()` 也不保证
  一定读到最新（本轮实测就是读不到）。
- **正确做法（已固化进脚本）**：断言落库结果一律走**独立连接**读取：
  ```python
  with db.engine.connect() as conn:
      row = conn.execute(T("SELECT status, review_result FROM review_tasks WHERE review_id=:r"),
                         {"r": rid}).fetchone()
  ```
  写/删同理用 `with db.engine.begin() as conn:`。
- **判据**：如果"接口返回 200 但断言读不到"，先怀疑**读的方式**，别急着改产品代码。
  （本例正是先通过 R6/R7 的反向断言反推出产品侧写入是好的。）
- 另：`DELETE … WHERE review_id=:x` 在 REPEATABLE READ 下会对该唯一索引取 gap lock，
  测试里自建/清理数据时注意别与待测写入撞上。

### 5.2 两条容易写错的断言
- 加复核意见只把 **`pending` → `in_review`**；已经是 `assigned` 的会保持 `assigned`
  （前端筛选页签只提供 待分派/已分派/已完成，并不使用 `in_review`，故这是符合现状的行为）。
  断言必须按实际语义写，否则会得出"功能坏了"的错误结论。

## 八、【P0 性能缺陷】Redis 密码配置不一致 → 单次调用 2–25 秒，且阻塞整个界面
用户问"还有什么体验优化方案 + 系统缺陷"，做**接口延迟画像**后挖出来的。

### 实测数据
- `GET /api/metrics/prometheus` = **6.6–8.1 秒**（全站中位耗时仅 **7ms**）
- `get_redis_client()` 连续调用 = 3.9s / 8.5s / **17s / 24s / 25s**
- `redis.ping()`（socket_timeout=1.0）= **1835ms**，返回
  `AuthenticationError: Client sent AUTH, but no password is set`
- `redis.ping()`（socket_timeout=0.5）= **9839ms**，同样 AUTH 错误
- 内置 Redis 日志显示它**反复"启动→请求关闭→退出"**（16:58/17:01/17:02/17:03）
- 网络探测：`127.0.0.1` / `::1` / `localhost` 三种地址**全部超时**（当时无进程），
  但 netstat 有大量到 6379 的 `TIME_WAIT`（说明连接曾建立过）
- `embedded_redis_active()` **只看进程内布尔标记**，秒回 True —— 与端口实际状态无关

### 机制（三层叠加）
1. `REDIS_PASSWORD` 在 `.env` / `key.env` 里**有值**，但内置 Redis **未启用鉴权**；
2. `core/redis_pool.py::get_redis_client()` 在 `if settings.REDIS_PASSWORD:` 分支里
   **对每次调用**都同步 `client.ping()`，失败后再重建无密码客户端
   （这段是我 2026-09-19 加的兜底，注释写"仅在配置了密码时才多一次探测，无额外开销"，
   **实际是每次调用都吃一次注定失败的往返**）；
3. `main.py::db_session_middleware` 用 **全局锁 `_db_lock`** 包住所有 `/api/` 请求
   → 那个 8 秒的指标请求**把整个界面的所有请求一起堵住 8 秒**。

### 修法
1. 清掉配置里不一致的 `REDIS_PASSWORD`（**`.env` 与 `key.env` 两处都要改**，只改一处会被覆盖）；
2. 把"密码不匹配"的探测结果**进程级缓存**（只探一次），不要每次调用都 ping；
3. 让 `/api/metrics/prometheus` 不占全局锁，Celery 队列长度改后台定时刷新 + 读缓存。

> ⚠️ 尝试跑"清空密码前后对照实验"时被安全策略拦下（涉及读取密码类配置），
> **未重试、未绕过**。结论仍成立：AUTH 错误与耗时是直接实测的。

## 十一、【已修】P0 性能缺陷：Redis 密码探测 —— 指标端点 13.6s → 28ms
### 逐层定位过程（值得复用）
1. 接口延迟画像发现 `/api/metrics/prometheus` **6.6–13.6 秒**（全站中位 **7ms**）
2. 拆分 `get_redis_client()` 内部各步：
   构造 client **1ms** / `_is_server_without_password` **0ms** / 无密码 ping **3ms**
   → 耗时**全部**在"首次带密码 ping"这一步：**10090ms**
3. 根因：`.env` 配了 `REDIS_PASSWORD` 而内置 Redis 未启用鉴权 → ping 抛
   `AuthenticationError`，而 **redis-py 把它当连接错误并退避重试**
   （`socket_timeout` 只约束单次 IO，管不到重试次数）；
   原代码**每次调用都探一遍** → 每次拿客户端都吃满 10 秒
4. 放大：`main.py` 的全局锁 `_db_lock` 串行化所有 `/api/` 请求 → 8 秒请求堵住整个界面

### 修法（`core/redis_pool.py`）
- 探测客户端禁用重试 `Retry(NoBackoff(), 0)`：同一失败路径 **13932ms → 2034ms**
- 探测结果**进程级缓存** `_PASSWORD_PROBE_RESULT`（key=host/port/db）：
  已探明"服务端无鉴权"后直接无密码连接；密码正确时也不再每次 ping
- 探测失败原因不明（服务端暂不可达）**不写缓存**，留待下次重探
- 客户端构造抽成局部 `_build()` 消除三处重复

### 实测效果
| 指标 | 修复前 | 修复后 |
|---|---|---|
| `get_redis_client()` | 5432 / 3227 / 9127 ms | **2 / 3 / 3 / 3 ms** |
| `/api/metrics/prometheus` | 13640 / 10876 ms | **28 / 10 / 10 ms** |

回归 9 脚本全绿（含两个 Redis 依赖用例）。提交 `54cb53f`。

> ⚠️ 配置治理仍待办：`REDIS_PASSWORD` 只在 `.env`、`REDIS_AUTOSTART` 只在 `key.env`
> ——**双份配置陷阱的实证**。清掉不一致项可让首次探测也免掉（未擅自改动密码配置）。

即：**"自动续期"从上线起就没生效过**。已统一为：先静默 refresh 并重试原请求，

### 9. 🟠 发现并修复：Redis 关闭阻塞 **44.6 秒**（每进程退出都付）
- 现象：任何短命进程（验证脚本/CLI）退出都要 ~45s，其中 30-44s 在 `atexit`。
- 根因：`core/redis_embedded.py::_shutdown_embedded()` 调 `shutdown(save=True)`，
  服务端**主动断连**，而 redis-py 默认把连接错误当「可重试」做指数退避。
  **这正是我上一轮在 `redis_pool.py` 修过的同一模式，但漏了这个文件。**
- 修法：同一处加 `Retry(NoBackoff(), 0)`。实测 **44.6s → 0.2s**，整进程 45s → 4.9s。
- 顺带把回归套件从 **9 分 01 秒**降下来（11 脚本）。

### 11. 浏览器验证新页面时抓到的**视觉级**坑（断言通过、界面仍不对）
给「演示数据复位」的确认框做危险色（红）时：
- 我加了 `customClass: 'fl-danger-confirm'` + `background-color: #ef4444`
- **断言读 `getComputedStyle().backgroundColor` = `rgb(239,68,68)` → PASS**
- **但截图里按钮仍是蓝色！**
- 用 CDP 读完整样式链才看清：`bgImage: linear-gradient(135deg, rgb(0,198,255), rgb(0,136,204))`
  —— **本项目全局主题给 `.el-button--primary` 加了蓝色渐变 `background-image`**，
  它盖在 `background-color` 之上。
- 修法：同时 `background-image: none`，且 hover/focus/active 各态都要盖
  （否则鼠标移上去又变回蓝渐变）。修后像素裁决 `rgb(224,64,64)` ✓
- **教训（新增铁律）**：改 Element Plus 按钮颜色时，只改 `background-color` 不够——
  必须检查 `background-image`。而且**`getComputedStyle().backgroundColor` 通过 ≠ 视觉正确**，
  断言要读 `backgroundImage` 或用**裁剪截图 + 像素取色**裁决。
  另外 `ElMessageBox` 的 `confirmButtonClass` 在 Element Plus 2.x **不生效**，要用 `customClass`。
- 附带工具：`fl_btncolor_probe.js`（读按钮 rect/样式链 + `Page.captureScreenshot` 带 `clip` 裁剪）
  比整页截图更容易做像素裁决 —— 背景不干扰取色。
