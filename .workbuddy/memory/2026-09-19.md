## 二、种子数据逻辑一致性缺陷（发现并修复 11 处）
- **现象**：`merge_suggestions` 与 `freeze_approvals` 存在自相矛盾记录：
  - V1 `pending` 却带 `reviewed_by`/`reviewed_at`（3 条：20/27/28）

  - V3 终态缺 `reviewed_by`（2 条：16/25）

## 三、Redis 密码不匹配导致持久化静默降级（重要）
- **现象**：日志 `Redis 不可用，将使用内存存储: Client sent AUTH, but no password is set`。配置里 `REDIS_PASSWORD` 有值（8 位），但本机 Redis **未启用鉴权** → AUTH 失败 → `get_redis_pool()` 返回 None。
- **影响**：会话历史持久化、JWT 黑名单、`LongTermMemory` 全部静默退化为进程内存储 —— **Task B 的"服务重启不丢对话"实际从未生效**。
- **修法**（`core/redis_pool.py`，两处）：
  1. 新增 `_is_server_without_password(err)`（仅匹配服务端明确回 `no password is set`，**密码错误不触发降级**，不构成安全降级）。
  2. `RedisPool._connect()` 抽出连接逻辑，命中该错误则 `_drop_password_and_rebuild()` 去密码重建连接池并重试一次（只重建一次）。
  3. `get_redis_client()`（LongTermMemory / 其他模块的统一入口）同样加去密码重试 —— 此前它绕过 RedisPool，修复未覆盖它会继续静默降级。
  4. `get_client()` 重构为 `_connect()` + 干净 `finally`，避免在 `except` 块内 `yield`（上下文管理器语义脆弱）。
- 实测：修复前 `LongTermMemory: Redis unavailable`；修复后 `Redis connected`，读写与跨实例读回均正常。

## 十六、发现并修复：止付冻结主线**从未成功过**（本轮最重要）
**这是"静默降级"家族里最恶劣的一个变体：不报错、不抛异常，只是静默什么都不做。**

- **现象**：库中 3 张 `freeze_orders` **全部 `status='failed'`**，执行处处产出 **0 条回执**。
- **根因**（`tools/freeze_executor.py::MockFreezeExecutor.execute`）：
  执行器按 `t.get("account")` / `t.get("bank")` 取账号，
  但**前端与创建接口写入的字段是 `account_number` / `bank_name` / `account_name`**
  （DB 里 JSON 实测就是这套）。取不到 → `if not account: continue` →
  **把每个账户都跳过** → `receipts` 为空 → 状态推导落到 `failed`。
- **为何长期无人发现**：全程不抛异常、接口返回 200、前端只显示"失败"，
  看起来像"业务失败"而不是"代码 bug"。而**回执**页签空着，也被当成"还没执行"。
- **修法**：新增 `_pick(d, *keys)` 按优先级兼容三套字段名
  （`account_number`/`account`/`account_no`/`card_number`、`bank_name`/`bank`、
  `account_name`/`holder`），并兼容纯字符串 / 单个 dict / 列表三种形态；
  消息里带上户名。
- **同时修掉的误导源头**：`database/workflow_models.py` 的列注释写着
  `# [{account, bank, holder}]`，与实际字段名不符 —— 正是它把执行器带偏的。
  已改为写明真实字段名 + 提示用 `_pick` 兼容取值。
- **对照**：`tools/doc_generator.py`（冻结文书）本来就正确读 `account_number`/`bank_name`，
  说明执行器是唯一的例外，不是全项目口径问题。

## 十七、状态推导口径修正（pending 不等于失败）
- 原逻辑：`success == len → executed；success > 0 → partial；否则 → failed`。
  问题：**只有 1 条 `pending`（已提交银行、等待回执）回执时判为 `failed`** ——
  「冻结指令已送达银行」却显示"工单失败"，语义错误。
- 新逻辑抽成 `_derive_freeze_status(receipts_dto)`（两处重复逻辑合一）：
  全 success → `executed`；存在 success 或 pending → `partial`；其余（全 failed）→ `failed`。

## 十九、顺手修掉一处**审批绕过**（合规缺口，判断项）
- `api_execute_freeze_order` 原条件：`role != 'admin' and status not in ('approved','failed','partial')`
  → **admin 可执行 `draft` / `pending_approval` / `rejected` 的工单**，
  即**完全绕过审批链直接冻结他人账户**。
- 判定：文档里写的意图是"仅 admin，或审批通过后自动执行失败时手动重试"，
  而 `failed`/`partial` 已覆盖重试场景 → 放行 draft/pending 属实现疏漏，非有意特权。
  冻结是法定强制措施，"审批通过"是**法律前提而非角色特权**，故改为**纯状态门控**
  （对所有人一致）。自动执行若抛异常会把工单置 `failed`，重试路径不会丢失。
- ⚠️ 这是行为变更（admin 不再能强行执行未审批工单）。若复赛演示确实需要 admin 特权，
  可回退此行；默认按合规收紧。

## 二十、探针方法论教训（两处自身踩坑）
1. **长事务快照**：探针里先 `db.session.query(Case).first()` 开了读事务，
   之后 API（另一线程）提交的新工单在**本进程查询里看不到**，一度误判"刚创建就查不到"。
   MySQL 默认 REPEATABLE READ，**探针读跨连接写入前必须先 `db.session.rollback()` 结束读事务**。
   已实测确认产品侧无此问题（14 → 15 跨连接写入可见，产品有 `db_session_middleware` 兜底）。
2. **外键删除顺序**：清理测试数据时 `DELETE FROM approval_flows` 被 `approval_nodes`
   的外键拒绝 → 必须先删子表 `approval_nodes`。
3. **又一次"取样赌运气"**：`KeyPerson.query.first()` 取到唯一那条 `is_active=False` 记录，
   一度误判碰撞功能全坏。**结论：验证前先确认样本本身符合预期，别用 `.first()` 赌。**
