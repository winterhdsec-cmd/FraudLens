## 2. 真实缺陷修复（P1，本次最有价值产出）

### vision.py 图片出域门禁绕过
- **根因**：`VisionAnalyzer` 自建 `OpenAI` client（`vision.py:39/46`），
  只校验 `api_key`，**完全不查 `DISABLE_CLOUD_LLM`**；且 `mask_messages`
  只处理文本、对 `image_url` 原样透传。
- **后果**：关闭云端开关后，文本路径已降级到本地，但**原始截图仍会
  base64 发出域** → 与「数据不出域」对外口径矛盾（9/16 已改为
  「本地优先＋出向脱敏」口径，此缺陷正是口径必须松动的技术根因）。
- **修法**：`analyze()` 入口先查 `cloud_llm_enabled()`，关闭时直接走本地
  OCR 并返回 `model=ocr_local`；`is_available()` 同步纳入开关判断；
  `_try_fallback` 加异常兜底（OCR 失败返回明确提示而非抛错）。
- **双向实测通过**：`DISABLE_CLOUD_LLM=1` → `ocr_local`（不出域）；
  `=0` → `qwen3.8-flash` 正确识别图内文字。

### docker-compose 漏注入 CLOUD_LLM_MASK
- 全文 `grep -c CLOUD_LLM_MASK docker-compose.yml` = **0**，即脱敏开关
  无法在 compose 层控制，只能靠代码默认值兜着。已在 backend + celery
  两个服务补注入 `${CLOUD_LLM_MASK:-1}`。
- 同时给 compose 顶部加安全注释：DB/REDIS/MINIO/JWT 的默认值是
  演示级弱口令，禁止用于真实环境（保留默认值以维持「零配置一键启动」，
  不改为强制必填——那会破坏无 .env 机器上的演示能力）。

### ⚠️ 批量改 import 的翻车教训（重要）
用正则批量插入 `from pathlib import Path` 时，脚本把该行插到了
**文档字符串之前 / `from __future__` 之前**，导致 2 个文件 SyntaxError：
- `pathb_elliptic.py`：`from __future__ imports must occur at the beginning`
- `smoke_han.py` / `smoke_stage2.py`：正则误把 `importlib.util`、`logging`
  合并进 `from pathlib import Path, importlib.util, logging` → invalid syntax

**正确做法**：改 import 必须用 `ast.parse()` 或 `py_compile` 逐个验证；
插入点要锚定在既有 import 块之后，而非文件首行。批量正则后**必须**
对全部涉改文件跑 `py_compile`。

## 7. 9 张空表 —— 结论：非缺陷，不造假填充

`accounts`/`persons`/`phones`/`evidence_items`/`review_opinions`/
`freeze_approvals`/`freeze_receipts`/`merge_suggestions`/`imported_fund_flows`

  实测**不成立**：230 条案件里 `extracted_entities` 非空的仅 1 条，

  （`gang.members?.length || gang.member_count_estimate || '-'`），
  空表**不会导致页面空白或崩溃**。
