## 一、缺陷清单（按严重度）

### P0 · Redis 密码配置不一致 ⚠️ 原始结论已复核修正（见下方「勘误」）

> **勘误（2026-09-20 二次核实，重要）**
>
> 本节原结论「单次调用 2–25 秒、拖慢整个界面」**在真实运行环境下不成立**，是
> **测量环境与生产不一致**造成的假象。复核过程与证据：
>
> | 场景 | `REDIS_PASSWORD` 实际取值 | `get_redis_client()` 实测 |
> |---|---|---|
> | **本地直跑**（`uvicorn main:app`，cwd=`backend/`） | `None`（key.env 无此项） | **2 / 2 / 2 ms** |
> | **容器部署**（compose） | 有值，且 redis 同源 `--requirepass` → **一致** | — |
> | 我原来的测量脚本 | 有值（**手工 load 了根目录 `.env`**） | 3227–13640 ms |
>
> **假象来源**：`main.py` 只 `load_dotenv('backend/key.env')`，**从不加载根目录 `.env`**；
> 而我的验证脚本写了 `load_dotenv(.env)` → `load_dotenv(key.env)`，`python-dotenv`
> 默认 `override=False`（**先加载者胜出**），于是 `.env` 里的 `REDIS_PASSWORD` 生效了，
> 而内置 Redis 并未启用鉴权 → 造出了「配置不一致」这个**只存在于脚本里**的组合。
>
> 另需澄清：`core/config.py` 的 pydantic-settings 配了 `env_file=".env"`，但该路径
> **按 cwd 解析**；从 `backend/` 启动时读不到，从项目根启动才会读到 —— 也就是说
> 这个不一致**只在「从项目根启动 + 且 key.env 未定义 REDIS_PASSWORD」时才会真实发生**。
>
> **保留下来的修复仍然有效且有价值**（属防御性加固，非线上问题修复）：
> `core/redis_pool.py` 的密码探测改为「**只探一次（进程级缓存）+ 禁用 redis-py 退避重试**」，
> 把「万一真的不一致」时的代价从 **13932ms 压到 2034ms**，正常路径 **2–3ms**。
>
> **教训（已写入项目记忆）**：验证脚本的配置加载方式必须与被测程序**逐字一致**；
> 否则测的是脚本环境，不是产品。为此本轮已把全部 12 个验证/维护脚本统一为
> 「只加载 `backend/key.env`」，并新增 `backend/check_config.py` 做只读配置自检。

**原始记录（保留以备追溯，请结合上方勘误阅读）**

**实测证据**（均为「手工加载 `.env` 后」的脚本环境）

| 测量对象 | 结果 |
|---|---|
| `get_redis_client()` 连续调用 | 3.9s / 8.5s / **17–25s** |
| `redis.ping()`（socket_timeout=1.0） | **1835ms** → `AuthenticationError: Client sent AUTH, but no password is set` |
| `redis.ping()`（socket_timeout=0.5） | **9839ms**，同样 AUTH 错误 |
| `GET /api/metrics/prometheus` | **6.6–8.1 秒**（全站中位耗时仅 **7ms**） |

**机制**

1. `.env` / `backend/key.env` 里配置了 `REDIS_PASSWORD`，但**内置 Redis 未启用鉴权**；
2. `core/redis_pool.py::get_redis_client()` 在 `if settings.REDIS_PASSWORD:` 分支里，
   **对每一次调用**都同步 `client.ping()`，失败后再重建一个无密码客户端；
3. 即：**每次拿 Redis 客户端，都要先吃一次注定失败的鉴权往返 + 一次重连**；
4. 内置 Redis 日志（`vendor/redis/runtime/redis-embedded.log`）还显示它
   被反复「启动 → 请求关闭 → 退出」（16:58 / 17:01 / 17:02 / 17:03 多轮），
   连接失败时会吃满 connect timeout。

**放大效应（这是体验上的真正杀手）**

`main.py::db_session_middleware` 用 **全局锁** 包住全部 `/api/` 请求：

```python
if path.startswith('/api/'):
    async with _db_lock:          # ← 所有 API 请求串行
        response = await call_next(request)
```

于是一个 8 秒的 `/api/metrics/prometheus` 会**把界面上所有请求一起堵住 8 秒**。

**修法（对照上方勘误阅读；① 为"仅在特定启动方式下才有意义"，② 已落地）**

1. ~~最直接：清掉配置里不一致的 `REDIS_PASSWORD`~~ —— 复核后确认本地直跑本就
   读不到该项，**无需改动**（改动 `.env` 属敏感操作，未执行）；
2. **治本 ✅ 已落地**：`core/redis_pool.py` 把「密码不匹配」的探测结果 **进程级缓存**
   （只探一次），并禁用 redis-py 的退避重试 —— 失败路径 13932ms → 2034ms，
   正常路径 **2–3ms**；
3. **隔离 ⏸ 未做**：让 `/api/metrics/prometheus` 不占全局锁 —— 依赖全局锁重构，
   按用户要求（架构改动暂缓）本轮不做。

### P0' · 【本轮复核新发现】`JWT_SECRET_KEY` 两份配置取值不同 —— 真实隐患 ⚠️ 待你决定

`backend/check_config.py` 是只读自检脚本，首次运行即报出：

```
JWT_SECRET_KEY    ★不一致   .env=frau****24   key.env=frau****od
[错误] 本地直跑与容器部署签发的 token 互不通用，切换部署方式会让所有用户被登出
```

- **为什么一直没暴露**：两次部署从不在同一会话里混用，且 token 存在 sessionStorage。
- **修法（需你决定改哪份，属密钥类操作，我未动）**：把两份统一为同一个值。
  改完 `python backend/check_config.py` 应显示 `一致`。
- **判定标准**：该检查已固化为 `check_config.py` 的常驻项，退出码非 0 即代表存在
  必须处理的配置问题。

### P0'' · 【本轮复核新发现】配置入口"谁生效"取决于启动方式（治理项）

- `main.py` 只 `load_dotenv('backend/key.env')`；
- `core/config.py` 的 pydantic-settings 又配了 `env_file=".env"`，**按 cwd 解析**；
- docker-compose 用根目录 `.env` 做 `${VAR:-default}` 插值再显式注入容器。

→ 三种入口叠加，同一个变量可能"生效 / 不生效 / 取到另一份值"。本轮已把
**全部验证与维护脚本**统一为「只加载 `key.env`」（与 `main.py` 逐字一致），
并新增 `backend/check_config.py`（只读，`--probe` 可探测 Redis 鉴权）作为长期防线。
**建议**：把 `core/config.py` 的 `env_file` 改为**绝对路径**或去掉，从根上消除
"取决于 cwd"的不确定性（涉及配置加载语义，本轮未动）。

## 二、体验优化方案（按投入产出排序）

### 立刻可做（半天内，风险低）

1. **补 loading 态**：给上述 5 个视图的表格加 `v-loading` + 骨架屏。
   这是**体感提升最明显**的一项——现在点进去是一片空白，用户以为坏了。
2. **消灭剩下 2 处 JSON 弹窗**（研判任务、审批流详情）。
3. **慢请求的可见反馈**：前端 axios 加超时阈值，
   `>1.5s` 显示「正在加载…」提示条，避免用户重复点击。
4. **危险操作二次确认统一化**：现有实现风格不一（有的 `ElMessageBox.confirm`、
   有的直接执行）。统一成一套确认组件，并统一文案格式。

### 值得做（1–2 天）

5. **空态引导**：目前多数空态只有「暂无数据」。改成
   「本案件暂无止付工单 → 【新建工单】」这种**带下一步动作**的空态。
6. **列表可用性**：默认排序（按时间倒序）、关键列固定、分页尺寸可选。
   现在部分表格列多且窄，需要横向滚动。
7. **全局错误提示统一**：401 自动跳登录、403/500 统一文案，
   不再把后端 `error` 原样抛给用户（如 `str(e)` 泄露内部异常）。
8. **演示模式**：一个按钮把演示数据恢复到初始状态
   （复用 `fix_seed_consistency.py` 的幂等修复 + `seed_empty_tables.py`）。
   答辩现场最怕误操作后数据被改乱。

### 加分项（赛前可选）

9. **首屏性能**：`/api/metrics/prometheus` 等非 UI 端点与 UI 请求隔离（见 P0）；
   首屏并发请求合并。
10. **可访问性/键盘**：表单回车提交、Esc 关弹窗、焦点管理。
11. **导出能力**：已有 PDF 报告；可补 Excel/CSV 导出（民警实际工作会用）。

### 2026-09-22 演示前自检新增：两个**同源**数据库缺陷（均已修复）

来源：用户要求"把项目起起来，确保能正常演示"，做演示前自检时实测发现。

| 缺陷 | 现象（实测） | 根因 | 状态 |
|---|---|---|---|
| **启动即锁库**<br>（最严重） | 后端起来一会儿后，任何写 `alert_records` 的操作 `Lock wait timeout exceeded`（默认 50s）→ 500；回归里 `_verify_alert_flow.py` 54.4s 超时失败 | `database/seed.py::_do_alert_data()` 的 `.delete()` **即使 0 行命中** 也会在 InnoDB 留表级意向锁，紧接着 `if count>0: return` **不结束事务**；而该函数跑在 `main.py::_background_init` 的 **daemon 线程**里、跑完即闲置 → 这个 thread-local session 变成**永久持锁者**（`data_locks` 实测：IX + 多条 X 记录锁） | ✅ 已修（两道） |
| **读到陈旧数据**<br>（用户可见） | 独立连接 INSERT 并提交后，`GET /api/alerts` 仍返回旧数据（写入前 87 条 → 写后仍 87 条，新 id 不可见） | MySQL 默认 **REPEATABLE READ** + thread-local session 被同一工作线程复用、事务从不结束 → 快照永不刷新 | ✅ 已修 |

**两者同源**：`db.session` 是 thread-local 且 `db_session_middleware` **不负责清理**，事务随线程延续。

**修法**
1. `seed.py`：`.delete()` 后**无论是否删到行**都结束事务（`dirty`→commit / 否则 rollback）；
   提前 `return` 前也 rollback 掉 count 那条只读事务。
2. `main.py`：`_background_init` 加 **try/finally 统一兜底**（commit → rollback → `session.remove()`），
   杜绝"后台线程留锁"这一类问题再犯。
3. `database/__init__.py`：MySQL 引擎设 **`isolation_level='READ COMMITTED'`**（仅 mysql），
   每条语句读最新已提交数据，且不加间隙锁（顺带减少锁冲突）。

**验证**
- 新增护栏 `backend/_verify_db_isolation.py`（4 项：隔离级别 / 跨连接可见性 / 事务卫生 / 无长时持锁事务）
- 套件 **11 → 12 脚本全绿（59s）**；`_verify_alert_flow` 从「54.4s 超时失败」恢复为「3.5s 通过」
- 真实浏览器**全路由体检 22/22 页干净**（0 崩溃 / 0 报错 / 0 个 4xx-5xx）
- 演示关键接口 14/14 返回 200

**诊断方法（可复用）**：`information_schema.innodb_trx`（谁挂着）→
`performance_schema.data_locks`（持了什么锁）→ `SHOW PROCESSLIST`（哪个连接）→
**停服对照**（确认归属）。本项目正是靠"停服后挂起事务归零"把嫌疑锁定到后端进程。

> 注：`_background_init` 所在的 daemon 线程模型、以及 thread-local session 不做请求级清理，
> 属于架构层面（用户已明确"架构暂不动"）。本轮只修**症状的根因路径 + 加统一兜底**，
> 未重构会话生命周期。


> ⚠️ 诚实边界不变：合成数据 ≠ 真实验证；止付冻结为 Mock；
> 「数据不出域」统一口径为**「本地优先 + 出向脱敏」**。
